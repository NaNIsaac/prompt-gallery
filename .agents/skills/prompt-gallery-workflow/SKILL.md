# Prompt Gallery 작업 흐름

사용자의 아이디어와 피드백을 실제로 시험한 사진 변환 프롬프트로 만들고, 요청 범위에 맞춰 테스트 또는 게시까지 끝낸다. 이 스킬이 요구하는 분리는 작업 시작의 Git 브랜치와 작업 공간 분리다.

## 단계별 완료 지점

- **스킬 호출 + 새 주제**(예: `$prompt-gallery-workflow 마네킹`): 전용 브랜치의 실제 상태 확인 → 제작·테스트 → **결과를 보여주고 사용자 중간 검토**까지 진행한다. 주제나 "테스트"만으로 PR 제출을 가정하지 않는다. 첫 결과는 작업 전체 완료가 아닌 **중간 결과·검토 대기**로 보고한다.
- **후속 수정·다른 사진 시험**: 같은 주제의 브랜치·작업 공간과 문구·기록을 이어 쓴다. 기존 PR이 있으면 요청 범위에 따라 같은 PR을 갱신하고 중복 생성하지 않는다. 문구를 그대로 시험하라는 요청이면 그대로 시험한다.
- **"결과 확정·PR 제출" 또는 확정한 결과의 제출 요청**: 자산·카탈로그 등록 → 로컬 검증 → 커밋·push → 원본 프로젝트 대상 Draft PR까지 진행한다. "좋다"만으로는 PR 제출이나 배포를 승인한 것으로 해석하지 않는다. 이미 확정한 결과에 대한 명확한 PR·배포 요청이나 중간 검토 없이 결과 선택까지 맡긴 명시적 요청이 있으면 같은 결정을 다시 묻지 않고 허용된 범위까지 진행한다.
- **"테스트만", "로컬에서만", "PR 만들지 마", "PR 없이"**는 계속 유효하다. 사용자가 명시적으로 제한을 바꾸기 전에는 제출하지 않으며, 일반 질문·검토 요청을 신규 제작·PR 요청으로 확대하지 않는다. 담당자의 병합·배포는 역할·실제 권한·해당 요청과 현재 커밋 검증이 확인된 경우에만 진행한다.

## 공유와 역할

이 스킬은 저장소에 커밋되어 있어 이 프로젝트를 clone하거나 fork한 기여자도 같은 지침을 사용한다. 개인 계정·소유자 이름이나 브랜치 push 가능 여부만으로 담당자로 단정하지 않는다.

- **기여자:** 별도 브랜치에서 제작·테스트·등록 자료를 준비하고 원본 프로젝트를 대상으로 PR을 제출한다. PR 링크와 현재 CI·담당자 검토 대기 상태까지 보고하면 제출 작업은 완료다. 검토 대기를 배포 실패로 표시하거나 병합을 기다리며 무기한 실행하지 않는다.
- **담당자:** 사용자가 이 프로젝트 담당자임을 밝혔거나 해당 역할이 확인되고, 실제 GitHub 병합 권한도 있으며, 명시적으로 병합 또는 배포를 요청한 경우에 병합 이후를 진행한다. PR 검토만 요청받았으면 검토 결과 보고까지 진행한다. 이 대화처럼 확인된 역할과 승인은 유지하되 실제 인증·권한이 달라지면 재확인한다. 스킬은 권한을 부여하지 않는다.
- 제출을 요청한 다른 기여자의 기본 경로는 PR 제출이다. 권한이 부족하면 만든 자료와 PR 상태를 보존하고 담당자에게 필요한 후속 단계를 알린다.

## 요청 범위와 작업 시작

1. 대화에서 확정한 아이디어·원문·최종 버전·참조 사진·피드백·게시 요청을 먼저 확인한다. 인계받거나 중단 후 재개하면 저장된 실제 입력과 파일도 확인한다. 이미 승인된 행동을 다시 묻지 않는다.
2. `git status --short`, 현재 브랜치·원격·작업 공간과 적용되는 `AGENTS.md`를 확인한다. 기존 변경을 보존한다. 같은 작업의 브랜치와 작업 공간이 있으면 이어 쓰고, 없으면 PR 대상 원본 저장소의 최신 기본 브랜치를 fetch한 뒤 그 커밋에서 전용 `codex/<주제>` 브랜치와 깨끗한 작업 공간을 마련한다. 진행 중인 다른 작업 브랜치에서 새 작업을 갈라 시작하지 않는다.
3. 원본 프로젝트인 base 저장소와 push할 head 저장소, 각 remote, 이 작업이 만든 브랜치·작업 공간·기준 커밋을 작업 기록에 남긴다. fork에서는 origin이 기여자 fork이고 upstream이 원본일 수 있으므로 이름만 보고 대상 저장소를 정하지 않는다. Codex 관리 작업 공간 도구가 있으면 첨부 목록을 먼저 확인하고 생성·복구·정리에 그 도구를 쓴다. 경로를 반환받은 후 실제 HEAD와 브랜치를 확인한다. 원격 추적 ref가 최신인지 도구의 기본값만 믿지 않는다.
4. 위 단계별 완료 지점에 따라 현재 단계를 정한다. 새 결과는 사용자 검토를 거치고, 결과 확정과 제출 요청 뒤 PR로 이어간다. 이미 받은 확정·게시 요청은 유지한다. 지원 대상을 넓혀 문구를 바꿔야 하면 변경 사실과 버전을 기록한다.

### 작업 브랜치 확인과 표시

이미지 생성·저장소 변경 전에 실제 Git 상태를 확인한다. 이 스킬 폴더 기준 `scripts/workflow-status.mjs`를 아래처럼 실행한다. BASE는 확인한 기준 ref 또는 이 작업에 기록한 시작 커밋이다. 예시 이름을 그대로 복사하지 말고 이번 작업의 실제 값을 넣는다.

```sh
node PATH_TO_SKILL/scripts/workflow-status.mjs --workspace WORKTREE_ROOT --expected-branch codex/TOPIC --base-ref BASE
```

스크립트는 실제 worktree 루트·현재 브랜치·HEAD·기준 커밋과 조상 관계를 확인하는 읽기 전용 게이트다. 불일치·detached HEAD·실행 실패를 해결하기 전에는 올바른 별도 브랜치라고 보고하지 않는다. 결과를 작업 기록에 저장하고 첫 진행 보고에 **브랜치명 / 실제 작업 공간 / 기준 커밋 / 신규 생성 또는 재사용**을 표시한다.

## 제작과 검토

- 제작 또는 테스트 단계에서는 [품질 기준](references/quality.md)을 읽는다. 사용자가 제공한 원문은 수정 요청이 없는 한 유지한다. 스타일·정체성 보존 조건과 장면 선택의 자유를 구분하고, 시험용 사진의 특정 사건을 모든 입력의 고정 조건으로 만들지 않는다.
- 이미지 생성은 사용 가능한 `imagegen` 스킬과 내장 이미지 생성 도구를 사용한다. 생성용 API 키를 요구하거나 CLI/API 방식으로 임의 전환하지 않는다. 새 가상 원본은 실제 사용자 사진과 구분한다.
- 각 테스트에는 해당 원본과 실제 최종 문구를 전달한다. 사진마다 몰래 추가한 지시나 보정한 결과를 같은 문구만 적용한 결과로 표시하지 않는다. 결과를 눈으로 비교하고, 문제는 필요한 부분을 수정해 다시 시험하거나 설명에 남긴다.
- 범용성을 요청했으면 범위에 맞는 서로 다른 입력을 시험한다. 인물 전용 요청에 풍경·동물 테스트를 일괄 강제하지 않는다. 사용자의 "좋다"만으로 요청하지 않은 입력 유형·기능·공개 작업을 늘리지 않는다.
- 작업 공간 안의 `output/imagegen/<주제>-<날짜>/`에 원본·결과·문구 버전·실제 도구 입력·파일 연결·검토를 보관한다. 공개할 파일은 게시 단계에서 `assets/images/`로 옮긴다. 토큰·개인 인증 정보는 기록하지 않는다.
- 일시적인 연결 실패는 동일 입력으로 제한적으로 재시도한다. 반복 실패나 장시간 무응답이면 완료된 파일과 실패 상태를 보존하고 상황을 알린다. 재개할 때 기존 요청·출력의 존재부터 확인한다. 실패를 성공으로 기록하지 않는다.

## 사용자 중간 검토

새 결과를 얻으면 [중간 검토와 채팅 선택지](references/review.md)를 읽는다. 원본·결과·실제 문구와 관찰한 장단점을 먼저 보여주고 현재 브랜치·작업 공간, **검토 대기 / PR 미생성 이유 / 선택 후 다음 행동**을 안내한다. 기본 선택지는 **결과 확정·PR 제출 / 수정 / 다른 사진으로 테스트**다. 사용 가능한 네이티브 질문 도구를 우선 쓰고, 도구가 없으면 번호 선택과 자유 입력을 제공한다. 무응답·기본 선택·시간 경과를 동의로 해석하지 않는다.

## 게시와 정리

사진 변환 예시를 제출하는 PR 본문에는 **입력 사진과 그 프롬프트로 생성한 출력 사진을 예시별로 짝지어 직접 표시**한다. 실제 적용 문구·버전과 생성 기록도 연결한다. 파일 경로나 링크만 나열하고 끝내지 않으며, 상세 형식과 주소 확인은 아래 게시 지침을 따른다.

Draft PR 제출 또는 등록·배포 범위에 들어가면 [게시·브랜치 수명주기](references/publishing.md)를 읽고 저장소의 [등록 원칙](../../../docs/prompt-publishing.md)을 따른다. 기존 저장소 규칙과 실행 가능한 스크립트를 재사용한다.

공통 흐름은 **전용 브랜치 → 제작·테스트 → 사용자 중간 검토·수정 → 결과 확정·PR 제출 요청 → 자산·카탈로그 등록 → 로컬 검사 → 커밋·push → 원본 프로젝트 대상 Draft PR 제출**이다. 담당자가 이어서 **현재 커밋의 필수 CI → 병합 → 병합 커밋의 Pages 배포 → 공개 확인**을 진행한다. 정리는 완료 상태와 브랜치 소유권을 확인한 뒤 각자의 작업에만 적용한다.

담당자가 배포를 요청했고 실제 권한과 검증이 충족됐으면 PR 생성·병합·배포·해당 작업 정리를 연속해서 진행한다. 기여자의 "배포해줘"는 원본 프로젝트 대상 PR 제출과 담당자 인계까지 진행한다. 외부 fork의 CI 실행이 담당자 승인 대기이면 그 상태를 보고하고 브랜치와 자료를 보존한다. 명시적으로 테스트만 요청했다면 PR을 생성하지 않는다. 결과 확정과 PR 제출 요청을 받았다면 결과 이미지와 문구 저장만으로 작업을 완료하지 않는다. CI·배포·공개 확인이 실패한 상태에서는 복구에 필요한 브랜치와 작업 공간을 남긴다.

단계 종료 응답에는 **현재 단계·실제 브랜치명·작업 공간·다음 행동**을 적는다. 중간 검토에서는 결과·실제 문구를 연결하고 "결과 검토 대기여서 PR은 아직 만들지 않았습니다"라고 안내한다. 생성하지 않은 커밋·PR·CI는 미생성·미실행으로 표시한다. 제출 단계에서는 **실제 커밋 SHA·PR URL·관측한 CI 상태**도 적는다. 제출 요청을 받았는데 PR이 없으면 완료라고 하지 말고 실제 차단 원인과 시도한 작업·남은 단계를 보고한다. 인증·권한·연결 문제를 근거 없이 가정해 PR을 생략하지 않는다. 담당자 배포는 공개 상세 링크도 제시한다. 배포 실행 시작과 성공, 브랜치 정리 예정과 실제 완료를 구분한다.

## 스킬 검증

스킬을 수정할 때는 [검증 요청 예시](references/validation-cases.md)로 적용 범위와 실행 판단을 점검한다. 사용할 수 있으면 실제 트리거 검사 도구와 공식 스킬 형식 검사를 실행한다. 도구가 없으면 대체 검토의 범위와 자동 호출을 직접 검증하지 못했다는 한계를 정확히 기록한다.
