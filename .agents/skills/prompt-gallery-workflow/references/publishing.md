# 게시·브랜치 수명주기

현재 저장소의 [기여 안내](../../../../CONTRIBUTING.md), [개발 흐름](../../../../docs/development.md), [테스트와 배포](../../../../docs/testing-and-deployment.md), [등록 원칙](../../../../docs/prompt-publishing.md)을 읽는다. 공통 절차와 기여자 제출, 담당자 병합을 아래처럼 구분한다.

## 역할·저장소·작업 시작

- Git 상태와 기존 첨부 작업 공간을 확인하고 기존 사용자 변경을 보존한다. 같은 요청의 작업은 재개하고 새 작업은 기준 브랜치에서 분리한다.
- base는 PR을 받을 원본 프로젝트, head는 기여 브랜치를 담은 저장소다. GitHub 저장소 관계와 실제 remote URL을 확인한다. fork에서는 origin이 본인 fork, upstream이 원본인 경우가 일반적이다. remote 이름만 믿고 origin/main을 원본 최신 상태로 간주하지 않는다. 기존 origin을 임의로 바꾸지 않는다.
- 원본 프로젝트에 직접 push할 권한이 없으면 본인 fork의 작업 브랜치에서 기여한다. 기존 fork가 있으면 재사용하고, 필요한 fork 준비도 요청 범위와 계정 권한 안에서 진행한다. 원본 저장소의 실제 기본 브랜치를 fetch하여 최신 커밋에서 전용 codex/<주제> 브랜치를 만든다.
- Codex 관리 worktree 도구가 있으면 첨부 확인·생성·보관에 사용한다. 없으면 Git의 별도 작업 공간을 쓸 수 있다. 반환된 경로·HEAD·작업 브랜치를 확인하고, 다른 미완료 작업은 복사하지 않는다.
- base와 head 저장소·remote·기준 커밋·이 작업 브랜치·작업 공간을 기록한다. 개인 계정명이나 push 권한만으로 담당자로 판단하지 않는다. 실제 담당 역할·GitHub 병합 권한·사용자의 병합 또는 배포 요청이 모두 있어야 담당자 단계를 진행한다. 이전 대화의 확인된 역할과 승인은 존중한다.

새 주제는 먼저 [채팅 중간 검토](review.md)를 진행한다. 결과 확정과 PR 제출 요청을 받으면 아래 등록·검증·Draft PR 절차를 완료한다. 이미 확정된 결과에 대한 명확한 PR·배포 요청은 다시 묻지 않는다. 중간 검토 대기는 PR 제출 실패가 아니며, 현재 단계·PR 미생성 이유·선택 후 다음 행동을 안내한다. Draft 제출만으로 병합·배포를 허용하지 않는다.

## 공통: 자산과 데이터

- 공개 문구와 실제 최종 시험 문구를 일치시킨다. 차이가 있다면 예시 설명과 기록에 명시한다. 같은 문구로 재시험하라는 요청에 등록 단계에서 문구 개선을 끼워 넣지 않는다.
- 원본·결과를 assets/images/ 안에 저장한다. Sharp로 무손실 WebP를 만들면 변환 전후 디코딩 픽셀을 비교하고, 썸네일은 결과 비율을 유지해 축소한다.
- 신규 고유 ID와 기존 최솟값보다 작은 order를 부여한다. 기존 항목과 상대 순서를 보존하고, 최신 base가 전진하면 충돌과 상단 배치를 다시 확인한다.
- 여러 예시는 examples에 각 결과·실제 치수·해당 원본·설명을 연결한다. 첫 예시는 카드의 결과·치수·referenceImages와 같게 한다. 원본을 서로 섞지 않는다.
- author는 실제 기여자나 제공자의 표시를 사용하고 저장소 담당자 이름으로 일괄 고정하지 않는다. sourceUrl에는 실제 출처를 쓴다. 토큰·불필요한 개인 경로는 공개 기록에 넣지 않는다.
- 현재 data/prompts.json의 스키마와 등록 규칙에 따라 실제 입력·추가 지시·원본 생성 문구·치수·SHA-256·생성 파일 식별자와 검토를 docs에 보관한다.

## 공통: 검증과 PR 제출

1. 원본·문구·결과 연결과 예시별 한계를 확인하고 npm run check를 완료한다. 필수 검증을 약하게 만들지 않는다. 코드·데이터를 이후 변경하면 영향에 맞게 재검증한다.
2. 기존 데이터 보존, 자산 치수·경로, 문구 일치, 문서 링크, git diff --check를 확인한다. 문서 편집은 UTF-8과 CRLF/LF를 고려한다.
3. 이번 파일만 명시적으로 stage·커밋하고 권한이 있는 head 저장소의 작업 브랜치로 push한다. 본인 fork를 사용할 때 upstream의 main에 push하지 않는다. 원본 base 저장소의 기본 브랜치를 대상으로 실제 Draft PR을 만든다. 이미 같은 주제의 PR이 있으면 그 PR을 갱신하고 중복 생성하지 않는다. fork의 경우 head 저장소와 브랜치를 정확히 지정한다.
4. PR에 최종 변경·원본과 결과·실제 테스트·한계·확인된 CI 상태를 쓴다. 본문은 구조화된 인자나 파일로 전달한다. Codex PR 첨부 도구가 있으면 생성한 PR을 채팅에 첨부한다. 기여자는 여기서 실제 브랜치명·worktree 경로·커밋 SHA·PR URL·확인한 CI 상태를 보고한다. PR URL은 GitHub 생성 결과에서 확인하며 예시 링크를 만들어 쓰지 않는다. 커밋이나 push만 끝내고 PR 제출 완료라고 하지 않는다. 이 상태를 웹 배포 완료로 표시하지 않는다.
5. CI 실패가 기여 내용 때문이면 같은 브랜치에서 수정한다. fork의 Actions가 담당자 승인 대기이면 그 사실을 알리고 다음 담당자 단계를 안내한다. 승인 대기를 해결하려고 권한·보호 규칙·workflow 이벤트를 바꾸거나 무기한 기다리지 않는다.

이미지 생성이나 검증에 실제 차단이 남으면 실패 원인과 실제 생성된 자료를 보존한다. 허위 성공 예시를 카탈로그에 등록하지 않는다. 현재 자료로 검토 가능한 범위와 제출 상태를 명시하며, PR을 만들지 못했으면 이유·시도·필요한 후속 단계를 보고한다.

## 담당자: 검토·병합·배포

1. 사용자가 검토·수락을 요청한 외부 기여자의 PR도 같은 기준으로 검토한다. 실제 입력·생성 예시·출처와 원본 연결, 변경 범위, 최신 base 반영·order 충돌을 확인한다. 요청받은 기존 PR은 채팅에 첨부한다.
2. 외부 fork의 workflow 실행 승인이 필요하면 실제 변경 내용을 검토한 뒤 권한 있는 담당자가 실행을 승인한다. GitHub의 [fork workflow 승인 절차](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks)를 따른다. 검사 성공·검사 실행 승인·PR 병합 승인을 서로 혼동하지 않는다.
3. 현재 PR head 커밋의 필수 CI 성공과 병합 가능 상태를 확인한다. 담당 역할과 실제 권한, 병합·배포 요청이 확인됐으면 중복 승인 질문 없이 병합한다. CI 실패·과거 커밋의 성공·실행 승인 대기 상태에서는 병합하지 않는다. 필요한 승인·보호 규칙을 우회하지 않는다.
4. 병합 커밋의 Actions CI와 Pages deploy 성공을 확인한다. PR의 deploy skipped는 배포 성공이 아니다. 실패하면 원인과 복구 상태를 알리고 작업 공간을 보존한다.
5. 실제 Pages의 해당 상세 페이지·카탈로그·예시 수·결과·원본·썸네일을 확인한다. 필요하면 파일 해시를 기록과 비교한다. 기여자에게 별도 메시지나 알림을 보내는 것은 그 전송 요청이 있을 때만 한다.

## 각자의 작업 정리

- 열린 PR·담당자 검토 대기·CI 승인 대기·실패 상태에서는 기여 브랜치와 수정에 필요한 자료를 보존한다. 기여자가 PR 제출을 완료했다고 해서 미병합 브랜치를 지우지 않는다.
- 병합·배포·공개 확인이 끝나면 이 작업에서 만들고 현재 사용자가 관리하는 브랜치만 정리한다. 담당자가 남의 PR을 병합했더라도 그 기여자의 fork 브랜치를 임의로 삭제하지 않는다. maintainer edits 권한도 브랜치 삭제 허가로 간주하지 않는다.
- PR head 저장소와 브랜치 소유권을 확인하고 삭제 대상 remote를 결정한다. 원격 tip이 병합된 PR의 head와 같은지 확인하며, 검증한 SHA에 한해 삭제되도록 조건을 건다. Git 예: git push --force-with-lease=refs/heads/BRANCH:EXPECTED_SHA HEAD_REMOTE :refs/heads/BRANCH. 단일 ref 삭제에만 적용하고 커밋 덮어쓰기·무조건 삭제는 하지 않는다. 조건부 삭제를 지원하지 않거나 ref가 전진했으면 보존한다. 이미 없는 ref는 정리 완료로 처리한다.
- 다른 worktree에서 사용하는 브랜치는 지우지 않는다. 전용 임시 작업 공간에 남길 변경·필요한 미추적 파일이 없는지 확인하고 관리 worktree는 archive 도구로 안전하게 보관·해제한다. 최신 base에 포함됐는지 확인한 뒤 자신의 로컬 브랜치는 일반 git branch -d로 삭제한다. 병합 방식 때문에 안전한 일반 삭제 검증이 되지 않으면 강제로 지우지 말고 이유를 보고한다.
- 원래 폴더가 다른 미완료 작업 중이면 현재 브랜치를 바꾸거나 전체 pull을 하지 않는다. 이번에 필요한 스킬 파일 같은 경로만 기존 차이를 확인해 반영한다. 다른 작업의 변경·브랜치·작업 공간은 보존한다.

기여자 완료 보고는 PR 링크와 CI·검토 대기 상태, 담당자 완료 보고는 공개 링크와 배포 확인 결과다. 실제 수행한 정리와 남긴 브랜치를 구분한다.
