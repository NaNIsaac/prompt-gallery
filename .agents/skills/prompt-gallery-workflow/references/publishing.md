# 게시·브랜치 수명주기

현재 저장소의 [개발 흐름](../../../../docs/development.md), [테스트와 배포](../../../../docs/testing-and-deployment.md), [등록 원칙](../../../../docs/prompt-publishing.md)을 우선 읽는다. 아래는 이 작업을 처음부터 끝까지 연결하는 기준이다.

## 시작과 재개

- Git 상태와 기존 첨부 작업 공간을 확인한다. 기존 사용자 변경을 stash·reset하거나 무관한 브랜치를 재활용하지 않는다.
- 새 작업이면 원격 기본 브랜치를 fetch한 다음 실제 최신 커밋에서 전용 `codex/<주제>` 브랜치를 만든다. 기본 브랜치가 main인지 원격에서 확인한다. 같은 요청의 중단·후속 작업은 적합한 기존 작업 공간과 브랜치를 재사용한다.
- Codex 관리 worktree는 생성·첨부 결과 경로를 사용하고 `HEAD`와 브랜치를 확인한다. 필요하면 반환된 detached HEAD에 작업 브랜치를 만든다. 소스 폴더의 미완료 작업은 복사하지 않는다. 관리 worktree 정리는 앱의 archive 기능으로 한다.
- 시작 시 저장소·원격·기준 커밋·작업 브랜치·작업 공간 경로를 식별할 수 있게 기록한다. 자격 증명은 포함하지 않는다.

## 자산과 데이터

- 공개 문구는 실제 최종 시험 문구와 일치시킨다. 달라야 한다면 차이를 공개 설명과 생성 기록에 명시한다. 요청 없는 문구 개선을 등록 과정에 끼워 넣지 않는다.
- 원본과 결과는 저장소의 `assets/images/` 안에 둔다. Sharp로 무손실 WebP를 만들 때는 변환 전후 디코딩 픽셀을 비교해 자르기·보정·크기 변경이 없음을 확인한다. 썸네일은 결과의 비율을 유지해 축소한다.
- 새 항목은 고유 ID와 기존 최솟값보다 작은 `order`를 부여한다. 여러 개면 요청 순서대로 새 값들을 배정한다. 기존 항목·order·상대 순서는 그대로 둔다.
- 여러 예시는 `examples`에 각각 결과·실제 치수·해당 원본·설명을 넣는다. 첫 예시는 카드의 결과·크기·referenceImages와 같아야 한다. 서로 다른 예시의 원본을 섞지 않는다.
- 현재 `data/prompts.json`을 읽어 스키마를 따르고 등록 시점의 최신 목록에 추가한다. 실제 입력·생성 문구·추가 지시·치수·SHA-256·원본 생성 파일 식별자를 `docs/image-generation-<날짜>-<주제>.json` 등에 기록한다. 검토와 관련 문서 링크도 등록한다. 홈 디렉터리 같은 불필요한 개인 경로는 공개 기록에서 제외한다.

## 검증·PR·병합

1. 원본·결과·문구 연결과 예시별 한계를 확인하고 `npm run check`를 완료한다. 실패를 무시하거나 필수 검증을 약하게 만들지 않는다. 검사 후 코드나 데이터가 달라졌다면 그 영향에 맞게 다시 확인한다.
2. 새 항목을 제외한 기존 데이터 보존, 자산의 실제 크기, 이미지 경로, 문구 일치, 문서 링크와 `git diff --check`를 확인한다. UTF-8과 CRLF/LF를 고려해 문서 제목·문단을 망가뜨리지 않는다.
3. 이 작업 파일만 명시적으로 stage하고 커밋·푸시한다. `git add .`로 다른 작업을 섞지 않는다. main 대상 PR에 최종 변경·검증·실제 한계를 적는다. 다중 행 본문은 구조화된 인자나 파일로 전달한다. Codex PR 첨부 도구가 있으면 생성한 PR을 이 채팅에 첨부한다.
4. GitHub에서 **현재 PR head 커밋의 필수 CI 성공**과 병합 가능한 상태를 확인한다. 배포 요청이 이미 있으면 추가 승인 질문 없이 PR을 병합한다. main이 전진했으면 최신 상태를 반영하고 신규 order의 충돌·상단 배치를 확인한 뒤 필요한 검사를 다시 실행한다.
5. **병합 커밋**의 Actions CI와 Pages deploy 작업 성공을 확인한다. PR에서 deploy가 skipped인 것은 Pages 배포 성공이 아니다. 실패하면 같은 작업에서 원인을 해결하며 상태를 정확하게 알린다.

GitHub 작업은 사용 가능한 연결 도구·CLI·기존 인증을 쓴다. 토큰을 출력하거나 파일·PR·로그에 넣지 않는다. 도구가 없다는 이유로 보호 규칙을 해제하거나 PR을 건너뛰지 않는다.

## 공개 확인과 정리

1. 실제 Pages URL에서 새 상세 페이지와 카탈로그를 확인한다. 공개 문구·예시 수·이미지 경로가 승인된 내용과 맞는지, 결과·원본·썸네일이 실제로 열리는지 확인한다. 필요하면 공개 파일 해시를 생성 기록과 비교한다.
2. PR 병합과 배포·공개 확인이 성공하고, 이번 작업 공간에 남길 변경이나 필요한 미추적 파일이 없는지 확인한다. 실패·미병합·사용자 검토 대기 상태에서는 복구에 필요한 브랜치와 작업 공간을 보존한다.
3. **이 작업에서 만든 브랜치만** 정리한다. 원격 브랜치는 병합된 PR의 head와 현재 ref가 같은지 확인하고, 그 SHA가 여전히 일치할 때만 삭제하도록 조건을 건다. Git에서는 `git push --force-with-lease=refs/heads/BRANCH:EXPECTED_SHA origin :refs/heads/BRANCH`처럼 이 작업의 단일 ref와 확인한 SHA를 명시한다. 이는 예상 SHA가 달라지면 실패하는 조건부 ref 삭제이며, 커밋을 덮어쓰는 force push나 무조건 삭제는 하지 않는다. 조건부 삭제를 지원하지 않으면 브랜치를 보존하고 보고한다. 이미 삭제된 원격 ref는 완료로 처리한다. 로컬에서는 최신 원격 기본 브랜치에 해당 브랜치의 커밋이 포함됐는지 확인한다. 일괄 삭제·다른 작업의 브랜치 정리는 하지 않는다.
4. 해당 브랜치를 사용 중인 다른 작업 공간이 있으면 삭제하지 않는다. 전용 임시 worktree를 먼저 안전하게 보관·해제한 뒤 로컬 브랜치는 일반적인 `git branch -d <branch>`로 삭제한다. 관리 worktree는 archive 도구를 사용한다. 기본 브랜치·사용자 현재 브랜치·남의 worktree는 손대지 않는다. 삭제 검증이 실패하면 강제 삭제로 우회하지 말고 남겨둔 이유를 보고한다.
5. 원래 작업 폴더가 다른 미완료 작업 중이면 그 브랜치를 main으로 바꾸거나 전체 파일을 pull하지 않는다. 이번에 추가한 스킬처럼 원래 폴더에서도 필요한 파일은 해당 경로만 안전하게 반영하고 그 상태를 보고한다.

성공 보고에는 공개 상세 링크와 실제 배포 확인 결과를 제시한다. 정리를 수행했다면 정리한 이번 브랜치·작업 공간을 명시하고, 남긴 것은 이유를 구분한다.
