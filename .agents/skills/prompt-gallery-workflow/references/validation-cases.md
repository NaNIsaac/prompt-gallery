# 적용 범위와 실행 판단 점검

스킬의 name·description만으로 적용 여부를 먼저 판단하고, 본문을 읽은 뒤 아래 작업을 어떻게 처리할지 독립적으로 검토한다. 자동 호출 시험과 사람이 읽고 판단한 검토는 구분한다. 이 문서를 실제 자동 트리거 도구의 성공 기록으로 간주하지 않는다.

## 적용해야 하는 요청

1. "짱구 세계의 주인공이 되는 프롬프트 테스트해줘. 첨부할 사진도 가상으로 만들어."
2. 진행 중인 갤러리 테스트 후: "최종 문구 그대로 다른 사진으로 해봐."
3. "이 갤러리 프롬프트를 풍경이나 반려동물 사진에도 쓸 수 있게 해서 검증해줘."
4. 승인된 예시가 있는 상태: "좋다. 이거 웹에 배포해줘. 브랜치도 정리하고."
5. "프로젝트를 fork했어요. 사진 변환 예시를 추가해서 원본 저장소에 기여 PR을 보내 주세요."
6. 담당자로 확인된 상태: "외부 기여자의 프롬프트 PR을 검토하고 CI 통과하면 병합·배포해줘."

## 적용하지 않아야 하는 요청

1. 갤러리 맥락 없이 "노을 지는 바다 이미지 한 장 만들어줘."
2. "이 사이트의 검색 버튼 CSS만 고쳐줘."
3. "오래된 브랜치를 전부 찾아서 정리해줘."

## 행동 시나리오

- 원래 폴더가 다른 작업으로 dirty이고 원격 main은 더 최신이다. 새 프롬프트의 준비·검증을 어디에서 시작하고 무엇을 보존하는가?
- 같은 요청의 작업 공간과 브랜치가 이미 있다. "다시 ㄱㄱ"를 받으면 어떤 상태부터 확인하는가?
- 사용자는 다른 원본으로 시험만 요청했다. 새 문구·배포·추가 입력 유형은 언제 허용되는가?
- 사용자는 범용 문구의 인물·풍경·고양이 예시를 승인했다. 공개 문구와 실제 입력을 어떻게 연결하고 예시 선택을 어떻게 검증하는가?
- 사용자가 배포를 요청했지만 PR의 과거 커밋만 CI 성공이고 현재 head는 실행 중이다. 병합·배포·브랜치 정리는 어디까지 진행하는가?
- Pages deploy는 성공했지만 새 상세 URL의 이미지 하나가 404다. 어떤 상태로 보고하고 어떤 작업 공간을 남기는가?
- 병합·배포·공개 확인은 성공했다. 정리 직전에 원격 작업 브랜치에 새 커밋이 추가됐다. 어떤 검증과 정리가 필요한가?

## 기여자·담당자 시나리오

- 원본 저장소에 push 권한이 없고 origin은 본인 fork, upstream은 원본이다. 최신 기준·push 대상·PR의 base와 head를 어떻게 고르는가?
- 일반 기여자가 "배포해줘"라고 했고 PR의 CI는 통과했다. 권한과 역할이 확인되지 않았을 때 완료 범위는 어디까지인가?
- 외부 fork의 PR에서 Actions가 담당자 승인 대기다. 제출 완료·CI 실패·담당자 후속 작업을 어떻게 구분하는가?
- 담당자가 기여자의 PR을 수락해 공개 확인까지 성공했다. 기여자 fork와 담당자 임시 작업 브랜치를 각각 어떻게 다루는가?
- 내부 협업자에게 브랜치 push 권한만 있다. 그것만으로 담당자 모드에 진입할 수 있는가?
- 담당자라고 밝혔지만 현재 인증에는 병합 권한이 없다. 무슨 상태와 자료를 남기는가?

형식 검사는 스킬 제작 도구의 `quick_validate.py`로 실행한다. 참조 링크와 저장소의 실제 배포 규칙도 확인한다. 스킬만 바꿨다면 새로운 이미지를 만들거나 기존 프롬프트·자산을 다시 생성하지 않는다.

## 중간 검토·선택지·브랜치 표시 회귀 사례

- `$prompt-gallery-workflow 마네킹` 또는 "마네킹 테스트": 실제 전용 브랜치 확인·경로·기준 표시 → 제작·테스트 → 결과·문구 표시 → 사용자 검토 대기. PR을 아직 만들지 않은 이유와 선택 후 다음 행동을 안내한다. 새 주제만으로 제출하지 않는다.
- 네이티브 질문 도구가 제공된다: 이미지와 문구를 보여준 뒤 **결과 확정·PR 제출 / 수정 / 다른 사진으로 테스트** 선택지를 도구로 제공한다. 지원 도구·모드를 무시하거나 버튼을 텍스트로 흉내 내면 실패다.
- 네이티브 도구가 없다: 번호 목록과 자유 입력으로 동일 결정을 받을 수 있게 한다. 불가능한 버튼 UI나 도구를 요구하지 않는다.
- "결과 확정·PR 제출" 응답: 현재 표시한 버전을 확정하고 등록·검증·커밋·push·실제 Draft PR까지 이어간다. PR URL과 관측한 CI 상태를 보고한다. 제출 요청을 받고 결과 저장만으로 끝나면 실패다.
- "수정"에 구체적 피드백이 없다: 필요한 변경 한 가지만 질문한다. 구체적 피드백이 있으면 같은 브랜치에서 새 버전을 시험하고 다시 보여준다.
- "다른 사진으로 테스트": 같은 문구·브랜치로 다른 원본에 시험하며 입력 유형 지정을 따른다. PR을 임의로 만들지 않는다.
- "좋다" 또는 "결과 확정"만 응답: 미관 확정과 제출 요청을 구분한다. 이미 제출 요청이 있으면 재질문하지 않는다.
- 질문의 기본 선택은 확정·PR 제출이고 사용자는 아직 응답하지 않았다: 시간 경과·기본 선택을 동의로 해석하지 않으며 게시 단계는 보류한다. 기록과 다음 행동을 남긴다.
- 이미 확정한 예시에 "웹에 배포해줘": 같은 검토 질문을 반복하지 않는다. 기여자는 PR·인계까지, 역할·권한이 확인된 담당자는 현재 CI 후 병합·배포까지 진행한다.
- `$prompt-gallery-workflow 마네킹 테스트만. PR 만들지 마`: 제한이 명시적으로 바뀌기 전에는 제출하지 않는다. 보관·테스트 경로를 안내한다.
- 같은 주제의 PR이 열린 상태에서 "최종 문구 그대로 다른 사진으로": 같은 문구로 시험하고 기존 브랜치·PR을 재사용한다.
- 실제 HEAD가 다른 브랜치 또는 detached 상태: workflow-status 게이트가 실패해야 하며 브랜치 증거를 꾸며 쓰지 않는다.
- 명확한 제출 요청 뒤 인증·연결 실패: 실제 오류와 커밋·원격 브랜치 상태, 시도와 남은 단계를 보고한다. 추정한 권한 부족을 이유로 PR을 생략하지 않는다.

## PR 사진 비교 점검

- 인물·풍경·반려동물 세 예시를 제출한다: PR 본문에서 세 쌍의 입력·생성 결과가 각각 짝지어 보이고, 실제 문구·생성 기록에 연결되어야 한다.
- 기여자 fork의 변경이며 Pages에 아직 없다: 실제 fork head 커밋의 이미지 주소를 사용한다. 원본 main이나 미배포 Pages 이미지로 대체하면 실패다.
- 결과를 수정하여 새 커밋을 push했다: PR의 비교 이미지·문구·기록을 같은 버전으로 갱신하고 주소를 확인한다. 이후 작업 브랜치가 삭제돼도 고정된 커밋의 이미지는 참조할 수 있어야 한다.
- 입력·출력 파일 링크만 있거나 로컬 output 경로다: 이미지가 본문에 직접 보이는지 확인하고 실제 접근 가능한 이미지 미리보기로 고친다.
- 문서만 바뀐 PR: 새 사진 생성을 강제하지 않는다. 기존 예시는 표시 참고임을 분명히 하며 신규 생성 성공으로 기록하지 않는다.

읽기 전용 브랜치 확인 스크립트의 회귀 검사는 저장소의 tests/workflow-status.test.mjs에서 실행한다. 스크립트는 브랜치나 파일을 변경하지 않으며, 실제 Git 상태 확인·사용자 중간 검토·PR 생성은 각각 다른 단계다.

## 오래된 checkout과 배포 환경 회귀 사례

- 새 세션에서 "지금 웹 배포 어디로 되고 있지?"라고 묻는다. 현재 폴더는 과거 콘텐츠 브랜치이며 pages.yml과 GitHub Pages 성공 기록이 있고 최신 main은 Cloudflare로 이관됐다. 현재 브랜치·미커밋 작업은 보존하고 최신 원본 기본 브랜치의 운영 문서·CI와 실제 배포 상태를 구분해 읽어야 한다. 로컬 pages.yml만 보고 GitHub Pages가 현재 운영이라고 답하면 실패다.
- PR의 CI와 Cloudflare 프리뷰가 성공했지만 main 운영 배포는 실패했다. 공개 배포 완료로 보고하지 않고 실패와 복구 자료를 보존한다.
- 원격 연결이 안 된다. 마지막 확인 ref와 로컬 구성을 구분하고 최신 운영 배포를 확인했다고 주장하지 않는다.
