# 적용 범위와 실행 판단 점검

스킬의 name·description만으로 적용 여부를 먼저 판단하고, 본문을 읽은 뒤 아래 작업을 어떻게 처리할지 독립적으로 검토한다. 자동 호출 시험과 사람이 읽고 판단한 검토는 구분한다. 이 문서를 실제 자동 트리거 도구의 성공 기록으로 간주하지 않는다.

## 적용해야 하는 요청

1. "짱구 세계의 주인공이 되는 프롬프트 테스트해줘. 첨부할 사진도 가상으로 만들어."
2. 진행 중인 갤러리 테스트 후: "최종 문구 그대로 다른 사진으로 해봐."
3. "이 갤러리 프롬프트를 풍경이나 반려동물 사진에도 쓸 수 있게 해서 검증해줘."
4. 승인된 예시가 있는 상태: "좋다. 이거 웹에 배포해줘. 브랜치도 정리하고."
5. "프로젝트를 fork했어요. 사진 변환 예시를 추가해서 원본 저장소에 기여 PR을 보내 주세요."
6. 담당자로 확인된 상태: "외부 기여자의 프롬프트 PR을 검토하고 CI 통과하면 병합·배포해줘."

## 적용하지 않아야 하는 요청

1. 갤러리 맥락 없이 "노을 지는 바다 이미지 한 장 만들어줘."
2. "이 사이트의 검색 버튼 CSS만 고쳐줘."
3. "오래된 브랜치를 전부 찾아서 정리해줘."

## 행동 시나리오

- 원래 폴더가 다른 작업으로 dirty이고 원격 main은 더 최신이다. 새 프롬프트의 준비·검증을 어디에서 시작하고 무엇을 보존하는가?
- 같은 요청의 작업 공간과 브랜치가 이미 있다. "다시 ㄱㄱ"를 받으면 어떤 상태부터 확인하는가?
- 사용자는 다른 원본으로 시험만 요청했다. 새 문구·배포·추가 입력 유형은 언제 허용되는가?
- 사용자는 범용 문구의 인물·풍경·고양이 예시를 승인했다. 공개 문구와 실제 입력을 어떻게 연결하고 예시 선택을 어떻게 검증하는가?
- 사용자가 배포를 요청했지만 PR의 과거 커밋만 CI 성공이고 현재 head는 실행 중이다. 병합·배포·브랜치 정리는 어디까지 진행하는가?
- Pages deploy는 성공했지만 새 상세 URL의 이미지 하나가 404다. 어떤 상태로 보고하고 어떤 작업 공간을 남기는가?
- 병합·배포·공개 확인은 성공했다. 정리 직전에 원격 작업 브랜치에 새 커밋이 추가됐다. 어떤 검증과 정리가 필요한가?

## 기여자·담당자 시나리오

- 원본 저장소에 push 권한이 없고 origin은 본인 fork, upstream은 원본이다. 최신 기준·push 대상·PR의 base와 head를 어떻게 고르는가?
- 일반 기여자가 "배포해줘"라고 했고 PR의 CI는 통과했다. 권한과 역할이 확인되지 않았을 때 완료 범위는 어디까지인가?
- 외부 fork의 PR에서 Actions가 담당자 승인 대기다. 제출 완료·CI 실패·담당자 후속 작업을 어떻게 구분하는가?
- 담당자가 기여자의 PR을 수락해 공개 확인까지 성공했다. 기여자 fork와 담당자 임시 작업 브랜치를 각각 어떻게 다루는가?
- 내부 협업자에게 브랜치 push 권한만 있다. 그것만으로 담당자 모드에 진입할 수 있는가?
- 담당자라고 밝혔지만 현재 인증에는 병합 권한이 없다. 무슨 상태와 자료를 남기는가?

형식 검사는 스킬 제작 도구의 `quick_validate.py`로 실행한다. 참조 링크와 저장소의 실제 배포 규칙도 확인한다. 스킬만 바꿨다면 새로운 이미지를 만들거나 기존 프롬프트·자산을 다시 생성하지 않는다.
